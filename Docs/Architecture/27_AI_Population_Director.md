# 27. AI Population Director: формирование карты расстояний, кандидатов и точек спавна

## Назначение документа

Этот документ фиксирует текущую архитектурную договорённость по `AI Population Director`.
Он нужен как рабочая точка возврата перед реализацией `LocationSearch`, промежуточного представления кандидатов и `SpawnPointFormation`.

Документ намеренно разделяет:

- уже работающий код;
- принятые концептуальные решения;
- временно допустимые упрощения;
- вопросы, которые пока нельзя честно закрыть без данных и замеров;
- возможные будущие расширения.

Основная цель ближайшего этапа — не реализовать весь Director, а корректно пройти цепочку:

```text
DistanceMap
→ LocationSearch
→ промежуточные кандидаты
→ SpawnPointFormation
→ постоянный SpawnPointList
```

## Обозначения статуса решений

В документе используются следующие пометки:

- **Зафиксировано** — решение уже принято или прямо следует из работающего кода.
- **TODO** — решение или код необходимы до завершения соответствующего этапа.
- **Будущее расширение** — возможность, которую не следует тащить в первую реализацию без необходимости.

## Граница ответственности Director

Director отвечает только за:

- поиск подходящих мест;
- формирование постоянных точек спавна;
- выбор готовых точек;
- расчёт бюджета создаваемой группы;
- формирование состава отряда;
- контроль общей динамической популяции;
- предотвращение повторного спавна из занятой точки.

Director не управляет дальнейшим поведением созданных ИИ, их маршрутами, преследованием или возвращением домой.

Маршрутные, квестовые и уникальные сценарные ИИ находятся за пределами этой системы.

## DistanceMap

### Назначение

`DistanceMap` — конкретный рабочий результат, необходимый функциям условий паттернов.
Это не общее название всей подготовки Director.

Для каждого гекса хранится один байт:

```text
старший полубайт — расстояние до дороги
младший полубайт — расстояние до поселения
```

Значения:

```text
0–14 — конечное расстояние
15   — далеко или недостижимо
```

Специальные начальные значения:

```text
обычный гекс → #FF
дорога       → #0F
поселение    → #F0
```

### Источники свойств

`DistanceMap.Initialize`:

1. читает `HextileID` из `Adr.Hextile`;
2. получает `FMapSurface.Passability` через `Adr.SurfPassability`;
3. выделяет `SURFACE_TYPE_MASK`;
4. определяет обычную поверхность, дорогу или поселение;
5. записывает начальное упакованное значение в `Adr.DistanceMap`.

Типы поверхности в текущем контракте:

```text
000 — обычная поверхность
110 — дорога
111 — поселение
```

Текущая тестовая таблица `DataBlock.HextileProperty` содержит поселения, но пока не содержит ни одного тайла с `SURFACE_TYPE_ROAD`.
До добавления временной или загружаемой дороги старший полубайт `DistanceMap` на тестовой карте будет оставаться равным `15`.

### Формирование расстояний

`DistanceMap.Build` обходит действительный прямоугольник карты по `Width × Height` и для каждого гекса проверяет до шести соседей odd-r.

Сетка соответствует принятой в проекте системе координат:

```text
нечётные строки смещены вправо относительно чётных
```

`UpdateFromNeighbor` уменьшает расстояния текущего гекса по значениям соседа.
Если за полный проход изменился хотя бы один байт, выполняется следующий проход.

Алгоритм работает без очереди и без дополнительного массива обхода.
Он использует сам `DistanceMap` и модифицируемый флаг `Build.ChangedFlag`.

### Размещение в памяти

Во время загрузочного процесса:

```text
Adr.DistanceMap = #4000
Size.DistanceMap = #0900
```

Размер `#0900` соответствует максимальной карте `48 × 48`.
Буфер расположен в области основного экрана и используется как временная память до запуска игрового мира.

Это отдельный буфер, не `Adr.MapMetadata`:

```text
Adr.DistanceMap = #4000  — временные расстояния Director
Adr.MapMetadata = #CA00  — постоянные метаданные карты и туман
```

`PostLoad.Launch` перед вызовом Director включает страницу карты, поэтому одновременно доступны:

- `Adr.DistanceMap` по `#4000`;
- `Adr.Hextile` и таблицы поверхностей на `Page.Hextile` по `#C000` и выше.

### Инварианты DistanceMap

- Дорога всегда имеет расстояние до дороги `0`.
- Поселение всегда имеет расстояние до поселения `0`.
- Конечное значение не превышает `14`.
- Значения `14` и `15` не распространяются дальше.
- Границы карты не рассматриваются как соседи.
- После завершения `DistanceMap.Build` соседние конечные значения одного поля отличаются не более чем на один шаг, если оба находятся в пределах насыщения.

## Термины: Pattern, Condition и Candidate

Важно не смешивать три разные сущности.

### SpawnPattern

`SpawnPattern` — описание варианта точки спавна и ссылка на функцию проверки его условий.

### ConditionID

`ConditionID` — индекс функции в таблице функций условий.

```text
ConditionID
→ таблица функций
→ конкретная функция проверки
```

Функция получает данные текущего гекса, может выполнять любую необходимую логику и возвращает `true` или `false`.

Она может:

- проверять тип текущего гекса;
- сравнивать расстояния до дороги и поселения;
- читать соседние типы гексов;
- оценивать лес, глубокий лес, болото, воду, горы или руины вокруг;
- проверять безопасную область;
- оценивать свободное пространство;
- использовать дополнительные условия конкретной карты.

**Зафиксировано:** `ConditionID` — индекс исполняемой функции, а не индекс набора числовых параметров.

**Зафиксировано:** отдельный `ConditionDataID` сейчас не вводится.
Если позднее одна функция должна будет обслуживать несколько наборов сохранённых параметров, этот вопрос можно открыть заново.

### PatternID

`PatternID` — индекс самого элемента в массиве `SpawnPattern`.

```text
ConditionID → какую функцию вызвать
PatternID   → какой SpawnPattern успешно прошёл проверку
```

В результат поиска должен попадать `PatternID`, а не `ConditionID`, потому что дальнейшим этапам нужны также таблица спавна, приоритет, флаги и другие свойства паттерна.

### Candidate

Кандидат — результат проверки одного гекса всеми активными паттернами.

```text
гекс
→ проверка SpawnPattern[0]
→ проверка SpawnPattern[1]
→ ...
→ набор всех PatternID, вернувших true
```

Кандидат не является готовым `SpawnPoint` и не обязан копировать входные расстояния или свойства поверхности.

## Структура SpawnPattern

В исходном описании была зафиксирована основа структуры:

```text
FSpawnPattern:
    ConditionID     DB    ; функция проверки
    SpawnTableID    DB    ; таблица доступных элементов отряда
    Priority        DB    ; приоритет паттерна
    Flags           DB    ; объединение и дополнительные свойства
```

Последующее обсуждение добавило два логически необходимых параметра:

```text
FormationWeight    ; вес среди несовместимых паттернов равного Priority
MinSpawnRadius     ; минимальная дистанция между формируемыми точками
```

Итоговый логический состав `SpawnPattern`:

```text
ConditionID
SpawnTableID
Priority
FormationWeight
Flags
MinSpawnRadius
```

Порядок полей, их физическая ширина и окончательный layout в коде пока не зафиксированы.

Кандидат не копирует эти параметры: `SpawnPointFormation` получает их из исходного `SpawnPattern` по установленному биту `PatternID`.

#### Совместимость

**Зафиксировано:** паттерны объединяются, только если их правила совместимости разрешают объединение.

Физический формат этой проверки пока не выбран. Возможны:

- маска совместимости;
- таблица совместимости;
- либо функция разрешения комбинации.

В исходной простой схеме разрешение задаётся через `Flags`, но точный битовый контракт ещё нужно определить.

## LocationSearch

### Ответственность

`LocationSearch` отвечает только на вопрос:

```text
какие гексы подходят под какие SpawnPattern
```

Он не должен:

- создавать постоянные `SpawnPoint`;
- выполнять пространственный мерж;
- применять `MinSpawnRadius`;
- разрешать конфликт приоритетов;
- применять вероятность формирования;
- учитывать сложность игры;
- рассчитывать бюджет отряда;
- учитывать текущую популяцию.

### Основной проход

Для каждого действительного гекса карты:

1. Прочитать `HextileID` и необходимые свойства поверхности.
2. Прочитать упакованные расстояния из `DistanceMap`.
3. Подготовить контекст текущего гекса.
4. Перебрать все активные `SpawnPattern`.
5. По `ConditionID` вызвать функцию каждого паттерна.
6. Собрать все `PatternID`, для которых функция вернула `true`.
7. Если совпадений нет, пометить гекс как не являющийся кандидатом.
8. Если совпадения есть, записать их 16-битную маску в `CandidatePatternMap[HexID]` для `SpawnPointFormation`.

### Почему поиск должен быть детерминированным

`LocationSearch` фиксирует свойства географии карты.
Вероятность на этом этапе усложнит анализ и сделает одинаковый гекс то подходящим, то неподходящим без изменения карты.

Поэтому:

```text
одинаковая карта + одинаковый набор паттернов
→ одинаковый набор кандидатов
```

Вероятность применяется позднее, только при разрешении допустимых вариантов или при runtime-спавне.

## Промежуточное представление кандидатов

Для каждого гекса хранится непосредственно 16-битная маска совпавших паттернов:

```text
CandidatePatternMap[HexID] = PatternMask

PatternMask = 0       → гекс не является кандидатом
bit 0                 → совпал PatternID 0
...
bit 15                → совпал PatternID 15
```

`PatternMask` является полным промежуточным представлением кандидата.

Позиция кандидата определяется индексом элемента карты:

```text
HexID = Y × MapWidth + X
```

Поэтому кандидат отдельно не хранит:

- координаты;
- расстояния;
- тип поверхности;
- приоритет паттерна;
- вес формирования паттерна;
- радиус паттерна;
- таблицу спавна паттерна;
- флаги паттерна.

Эти данные читаются по `HexID` из карты либо по установленным битам из исходных `SpawnPattern`.

Для карты 48×48 требуется:

```text
2304 гекса × 2 байта = 4608 байт = #1200
```

Логически младший байт хранит `PatternID 0–7`, старший — `PatternID 8–15`.
Физически карта может быть массивом последовательных слов либо двумя байтовыми плоскостями по `#0900` байт.
Конкретное размещение в памяти пока не выбрано.

Текущий контракт ограничивает карту шестнадцатью активными паттернами.
Если впоследствии потребуется больше, расширять нужно одновременно:

- `CandidatePatternMap`;
- `FSpawnPoint.PatternMask`;
- `FSpawnUnit.RequiredMask` и `FSpawnUnit.ForbiddenMask`.

До такого расширения количество активных паттернов должно явно проверяться: `ActivePatternCount > 16` является ошибкой конфигурации, а не причиной молча отбросить лишние совпадения.

### Открытый вопрос перезаписи DistanceMap

Перезапись текущего байта безопасна только при следующем контракте:

```text
функция условия читает расстояния только текущего гекса
```

Если функция вправе читать расстояния соседних гексов, последовательный проход разрушит данные:

```text
предыдущий гекс уже содержит байт PatternMask
→ функция следующего гекса принимает маску паттернов за расстояния
```

Поэтому до реализации необходимо выбрать одно из решений.

#### Вариант A: ограничить функции условий

Функция получает расстояния только текущего гекса.
Окружение она может анализировать по `Adr.Hextile` и другим постоянным данным, но не по соседним байтам `DistanceMap`.

Тогда `DistanceMap` можно безопасно преобразовывать на месте в одну из байтовых плоскостей `CandidatePatternMap`.

Один байт `DistanceMap` становится одной из двух байтовых плоскостей `CandidatePatternMap`.
Для второй плоскости всё равно требуется ещё `#0900` байт.

#### Вариант B: сохранить DistanceMap до завершения поиска

Кандидаты записываются в другой буфер.
После полного `LocationSearch` `DistanceMap` можно освободить или переиспользовать.

## SpawnPointFormation

### Ответственность

`SpawnPointFormation` получает все найденные кандидаты и превращает их в распределённый по карте постоянный `SpawnPointList`.

Он отвечает за:

- разрешение нескольких паттернов одного гекса;
- совместимость паттернов;
- разрешение несовместимых паттернов одной логической маски через `Priority` и `FormationWeight`;
- пространственное объединение близких кандидатов;
- формирование окончательной структуры точки;
- ограничение результата фактической вместимостью буфера;
- стабильные индексы `HomeID`.

Способ кодирования совместимости и геометрические последствия конфликта ещё требуют уточнения, но порядок выбора самих паттернов уже зафиксирован.

### Граница принятого решения

На текущий момент договорённость заканчивается следующим:

- все ненулевые маски из `LocationSearch` участвуют в `SpawnPointFormation`;
- внутри маски одного кандидата совместимые паттерны объединяются;
- внутри этой маски среди несовместимых паттернов сохраняется наибольший `Priority`;
- несовместимые паттерны меньшего приоритета отбрасываются;
- равноприоритетные несовместимые паттерны выбираются по `FormationWeight`;
- меньший кандидат внутри радиуса большего поглощается, если их наборы паттернов совместимы;
- кандидат вне большего радиуса остаётся на своей позиции;
- радиус поглощающей точки после мержа не увеличивается;
- обход нельзя обрывать из-за заполнения будущего `SpawnPointList`;
- после полного формирования при нехватке места первыми отбрасываются меньшие приоритеты.

Открытыми остаются правила равных радиусов, вычисление радиуса маски с несколькими паттернами, пространственный конфликт несовместимых кандидатов с разными координатами и выбор точек внутри одного приоритета при переполнении списка.

### Почему не используется простая случайная выборка координат

Полностью случайный выбор кандидатов может:

- собрать точки в одном углу;
- оставить подходящие области пустыми;
- дать сильно различающийся результат на одной карте;
- потратить вместимость списка до обработки конца карты.

Основное пространственное распределение должно определяться географией найденных кандидатов.
`FormationWeight` выбирает вариант паттерна при конфликте и не должен заменять это пространственное распределение.

## Зафиксированная модель: все кандидаты, затем схлопывание

Принята следующая последовательность:

```text
каждый подходящий гекс
→ временная точка-кандидат на своей позиции

затем

близкие кандидаты
→ объединяются по радиусам и совместимости

оставшиеся кандидаты
→ становятся SpawnPoint
```

Так каждый кандидат сначала участвует в формировании, а результат повторяет реальные области местности.

«Каждый кандидат является временной точкой» — логическая модель алгоритма.
Она не требует заранее выделять 2304 полных структуры `FSpawnPoint`.
Физически кандидат остаётся 16-битной маской `CandidatePatternMap[HexID]`, пока не переживёт этап мержа.

### Основное правило радиуса

Пусть существуют кандидаты `A` и `B`:

```text
RadiusA > RadiusB
Distance(A, B) < RadiusA
```

Если их паттерны совместимы:

```text
B объединяется с A
B перестаёт быть самостоятельной точкой
паттерны B добавляются в A
```

Если два разных кандидата внутри радиуса содержат несовместимые паттерны, ещё нужно определить, применяется ли к ним то же правило `Priority → FormationWeight` и какая координата после этого сохраняется.

В текущем рассуждении использовалось строгое условие `Distance < Radius`, соответствующее формулировке «точка ближе заданного радиуса».

**TODO:** окончательно зафиксировать границу `<` или `<=`, чтобы сосед на расстоянии, точно равном радиусу, обрабатывался одинаково во всех функциях.

Если центр меньшего кандидата не находится внутри радиуса большего:

```text
B остаётся на своей позиции
```

Гексагональное расстояние должно рассчитываться принятой в проекте odd-r функцией расстояния.

### Радиус после мержа не увеличивается

Это принципиальное требование текущей модели.

```text
A поглотил B
→ радиус A остался прежним
```

Запрещено автоматически расширять радиус итоговой точки за счёт поглощённого кандидата.
Иначе возникнет цепное поглощение:

```text
A поглотил B
→ увеличил радиус
→ достиг C
→ снова увеличил радиус
→ одна точка поглотила большую часть области
```

Мерж объединяет совместимые биты `PatternMask`, но не геометрически раздувает область точки.

### Равные радиусы — не решено

Принятое правило описывает поглощение меньшего радиуса большим.
Поведение двух кандидатов с одинаковым `MinSpawnRadius` в обсуждении не было зафиксировано.

До реализации необходимо решить:

- могут ли равные радиусы мержиться;
- какой кандидат сохраняет координату;
- требуется ли детерминированное правило равенства и каким оно должно быть.

Меньший `HexID`, центр локальной области и детерминированный seed рассматривались только как возможные варианты и не являются частью принятой схемы.

### Порядок обработки — не решено

Принято только отношение между большим и меньшим радиусами: меньший кандидат не должен поглощать больший.
Точный порядок обхода ещё не зафиксирован.

Возможная основа порядка:

```text
больший MinSpawnRadius
→ меньший MinSpawnRadius
```

Это пока предложение реализации, а не окончательный контракт сортировки.
Правило для равных радиусов остаётся открытым.

`Priority` разрешает конфликт несовместимых паттернов и используется при прореживании из-за нехватки места.
Будет ли он дополнительно влиять на пространственный порядок обработки кандидатов, пока не решено.

### Несколько паттернов одного кандидата

Один гекс может соответствовать нескольким паттернам.

`LocationSearch` сохраняет все совпадения в одной 16-битной маске и ничего на этом этапе не выбирает.

`SpawnPointFormation` разрешает маску в следующем порядке:

1. Совместимые паттерны сохраняются вместе.
2. Для несовместимых паттернов сравнивается `Priority`.
3. Паттерны меньшего приоритета отбрасываются.
4. Среди оставшихся равноприоритетных несовместимых паттернов выполняется выбор по `FormationWeight`.

Например, совместимые `Forest` и `NearSwamp` остаются в одной маске точки.
Несовместимые `Forest` и `BanditCamp` сначала сравниваются по `Priority`, а при его равенстве — по `FormationWeight`.

Кандидат хранит только `PatternMask`; `Priority`, `FormationWeight` и `Flags` читаются из таблицы `SpawnPattern`.

### Эффективный радиус кандидата — не решено

Если один кандидат содержит несколько сохранённых паттернов с разными радиусами, необходимо определить его эффективный радиус.

Возможные правила:

- максимальный радиус среди паттернов;
- радиус главного паттерна с наибольшим приоритетом;
- отдельный результат функции разрешения комбинации.

Ни одно из этих правил пока не принято.

### Мерж двух кандидатов

Если меньший кандидат находится в радиусе большего и их наборы паттернов совместимы:

- основная координата остаётся у поглощающего кандидата;
- совместимые паттерны двух масок объединяются;
- радиус не увеличивается;
- поглощённый кандидат помечается обработанным;
- постоянный `HomeID` ещё не назначается.

`HomeID` появляется только после формирования окончательного `SpawnPointList` и равен индексу элемента в нём.

### Пространственный конфликт несовместимых кандидатов — не решено

Для несовместимых паттернов одной логической маски правило `Priority → FormationWeight` зафиксировано.
Для двух разных координат внутри радиуса пока не определено, применяется ли оно тем же способом.

Нужно решить:

- остаются ли обе несовместимые координаты самостоятельными точками;
- применяется ли между ними `Priority → FormationWeight`;
- поглощается ли меньшая координата, если все её паттерны проиграли;
- может ли более приоритетный паттерн меньшего кандидата заменить координату большей точки;
- какой радиус сохраняется после такой замены;
- могут ли специальные несовместимые типы оставить обе точки рядом.

## Priority и независимые вероятности

`Priority`, вероятность формирования точки, вероятность работы готовой точки и вероятность конкретного юнита относятся к разным этапам.
Их нельзя объединять в одно поле `Chance`.

### Priority

`Priority` не является вероятностью.
В `SpawnPointFormation` он отбирает допустимые варианты среди несовместимых паттернов одной формируемой маски:

```text
больший Priority
→ паттерн сохраняется

меньший Priority
→ несовместимый паттерн отбрасывается
```

Вес паттерна меньшего приоритета не сравнивается с весом победившего паттерна.

### SpawnPattern.FormationWeight

`FormationWeight` применяется только между несовместимыми паттернами одной формируемой маски, имеющими одинаковый наибольший `Priority`.

```text
WolfForest:
    Priority = 2
    FormationWeight = 80

BearForest:
    Priority = 2
    FormationWeight = 20
```

Если оба паттерна совпали и несовместимы, `WolfForest` получает вес 80, а `BearForest` — 20.
Этот вес выбирает разновидность паттерна, но не случайную координату по всей карте.

Если одновременно присутствует:

```text
AncientMonster:
    Priority = 3
    FormationWeight = 1
```

сначала побеждает `Priority = 3`.
Его вес `1` не сравнивается с весами `80` и `20` паттернов меньшего приоритета.

Кандидат не копирует `Priority` и `FormationWeight`: `SpawnPointFormation` читает их из `SpawnPattern` по `PatternID`.

### Доступность готовой SpawnPoint

После формирования `SpawnPointList` карта больше не сканируется.
Перед runtime-выбором точка считается доступной, если:

- она включена;
- её `HomeID` не занят живой группой;
- завершён `Cooldown`;
- общий лимит популяции не заполнен;
- таблица точки содержит доступных юнитов;
- дополнительные runtime-условия точки остаются допустимыми.

### Необязательный SpawnPoint.SelectionWeight

Отдельный вес может определять, насколько часто готовая точка выбирается среди доступных.
Для первой реализации он не требуется.

Если одновременно использовать `SelectionWeight` и `SpawnChance`, две вероятности будут влиять на частоту работы одной точки, что усложнит баланс.

### SpawnPoint.SpawnChance

Применяется позднее, во время работы готовой точки:

```text
точка выбрана и доступна
→ SpawnChance определяет успешность попытки
```

Эта вероятность не участвует в `LocationSearch`.
`SpawnChance` определяет активность уже существующей точки во времени, а не её появление на карте.

Простой первый вариант runtime:

```text
равномерный случайный выбор доступной SpawnPoint
+
SpawnPoint.SpawnChance
```

### SpawnUnit.Chance

Применяется при формировании состава уже создаваемого отряда.

```text
SpawnPoint выбран
→ рассчитан SpawnBudget
→ Chance конкретного элемента определяет его попадание в отряд
```

Эта вероятность влияет только на состав отряда и не участвует в поиске места, формировании точки или выборе точки.

### Три зафиксированных уровня вероятности

```text
SpawnPattern.FormationWeight
    → выбор паттерна при формировании точки

SpawnPoint.SpawnChance
    → успешность попытки готовой точки

SpawnUnit.Chance
    → попадание конкретного юнита в отряд
```

`SelectionWeight` остаётся отдельным необязательным четвёртым механизмом выбора готовой точки.

### Воспроизводимость

Поскольку `FormationWeight` использует случайность, результат формирования должен быть воспроизводим либо сохранён:

- окончательный `SpawnPointList` сохраняется в состоянии карты/сессии;
- либо формирование использует сохранённый seed.

Повторная загрузка одного сохранения не должна бесконтрольно перестраивать точки иначе.

## Вместимость SpawnPointList

### Почему MAX_SPAWN_POINTS пока не определён

Физическая вместимость зависит от двух ещё не закрытых решений:

- окончательного размера `FSpawnPoint`;
- выделенного под список буфера.

Позднее предел вычисляется как:

```text
SpawnPointCapacity = SpawnPointBufferSize / FSpawnPoint
```

До этого фиксировать произвольный `MAX_SPAWN_POINTS` не требуется.

При этом существующий `FAIDirector.SpawnPointNum` уже является одним байтом.
Даже если отдельная константа `MAX_SPAWN_POINTS` пока отсутствует, формат счётчика физически не сможет представить количество больше 255.

Если будущий `HomeID` также останется байтом, а значение `#FF` будет означать «точки нет», допустимыми идентификаторами станут `0–254`.
Окончательно этот предел должен определяться вместе с layout `FSpawnPoint`, `FAIGroup` и правилами специального значения `HomeID`.

### Нельзя прекращать формирование при заполнении будущего списка

Если остановить обход после заполнения первых записей:

- преимущество получит начало карты;
- конец карты останется без точек;
- результат будет зависеть от линейного порядка гексов.

Поэтому логическая последовательность должна быть такой:

```text
все кандидаты
→ полный пространственный мерж
→ полный временный набор точек
→ проверка физической вместимости
→ прореживание при необходимости
→ запись постоянного SpawnPointList
```

### Прореживание при нехватке места

Если после мержа точек больше, чем помещается, сначала отбрасываются точки меньшего приоритета.

На этом принятая часть правила заканчивается.

До реализации необходимо определить:

- как вычисляется приоритет точки, содержащей несколько паттернов;
- как выбирать точки внутри одного приоритета, если весь уровень не помещается;
- что делать, если даже точек высшего приоритета больше физической вместимости.

Выбор «наиболее пространственно ценных» точек и использование `HexID` как правила равенства обсуждались только как варианты и пока не приняты.

## Предварительная структура SpawnPoint

В исходном описании использовалась структура:

```text
FSpawnPoint:
    HexIndex        DW
    PatternMask     DW
    SpawnTableID    DB
    Cooldown        DB
    SpawnChance     DB
    Flags           DB
```

`HexIndex` является стабильным координатным ключом:

```text
HexIndex = Y × MapWidth + X
```

Индекс элемента в постоянном `SpawnPointList` является `HomeID`.
Сам `HomeID` внутри точки не хранится.

### Поля структуры и открытые вопросы

#### PatternMask DW

Это рабочий контракт первой реализации: поле напрямую принимает объединённую маску из `CandidatePatternMap` и хранит `PatternID 0–15`.
При мерже совместимых кандидатов соответствующие биты объединяются.

Ограничение в шестнадцать активных паттернов принято осознанно и не является открытым вопросом первой реализации.
Если реальные карты потребуют больше, ширина набора должна быть увеличена одновременно в `CandidatePatternMap`, `FSpawnPoint.PatternMask`, `FSpawnUnit.RequiredMask` и `FSpawnUnit.ForbiddenMask`.

#### SpawnTableID

Один паттерн имеет одну таблицу, но объединённая точка может содержать несколько паттернов.

Необходимо определить:

- выбирается таблица главного паттерна;
- используется общая таблица, управляемая `RequiredMask`/`ForbiddenMask`;
- формируется комбинированная таблица;
- либо точка хранит несколько таблиц.

Исходное описание `FSpawnUnit` уже содержит `RequiredMask` и `ForbiddenMask`, поэтому общая таблица с фильтрацией по набору паттернов является возможным направлением, но не зафиксированным решением.

#### Cooldown и SpawnChance

Эти поля относятся к runtime-жизни готовой точки и не нужны промежуточному кандидату.

## Что хранит карта

Минимально карта должна предоставить или выбрать:

- готовый `SpawnPointList`; либо
- список активных `SpawnPattern`, по которым Director сформирует точки;
- базовые настройки Director для этой карты.

Каждый активный `SpawnPattern` логически предоставляет:

```text
ConditionID
SpawnTableID
Priority
FormationWeight
Flags
MinSpawnRadius
```

Карта не обязана отдельно задавать ожидаемое количество совпадений каждого паттерна или рассчитанные вероятности их появления.

Количество кандидатов естественно определяется:

- формой местности;
- типами гексов;
- расстояниями до дорог и поселений;
- логикой функций условий.

### Необязательные дизайнерские квоты

Требования вида:

```text
не более двух редких точек
не менее пяти обычных лесных точек
ровно одна уникальная точка
```

являются отдельным механизмом `MinPointCount`/`MaxPointCount`.

Они не нужны для базового пространственного распределения.
Базовое распределение обеспечивается участием всех кандидатов и последующим схлопыванием по радиусам.

**Будущее расширение:** добавить квоты только для явно поставленной дизайнерской задачи.

## Сложность игры

Сложность не участвует в `LocationSearch` и не должна менять базовую географию `SpawnPointFormation` без отдельного дизайнерского требования.
География подходящих мест должна оставаться понятной и стабильной.

Основные параметры сложности применяются позднее:

- `PopulationLimit`;
- `SpawnBudget`;
- количество попыток за проход;
- частота периодических запусков Director;
- `Cooldown`;
- общие коэффициенты успешности спавна.

Тогда одна и та же точка на разных сложностях остаётся на месте, но создаёт разные по стоимости и размеру отряды.

## Initial, Periodic и External

После формирования `SpawnPointList` повторное сканирование карты не выполняется.

### Initial

Первичное заселение перед началом игры.
Использует готовые точки и отдельные начальные настройки бюджета/попыток.

### Periodic

Плановое восстановление популяции:

- проверка активных групп;
- вычисление занятых `HomeID`;
- пересчёт текущей стоимости популяции;
- обновление `Cooldown`;
- выбор доступных точек;
- расчёт бюджета;
- создание новых групп.

### External

Внеочередная попытка по событию.
Использует готовый `SpawnPointList` и не запускает заново `DistanceMap` или `LocationSearch`.

### Отдельный вопрос начального распределения групп

Даже распределённый `SpawnPointList` не гарантирует, что случайно выбранное подмножество начальных групп окажется равномерным.

Это отдельная задача `Initial.Spawn`, а не причина менять `LocationSearch`.

## Примеры работы SpawnPointFormation

### Большой однородный лес

Каждый лесной гекс соответствует `Forest`, радиус равен пяти.

```text
все лесные гексы становятся кандидатами
→ все кандидаты имеют одинаковый радиус
→ принятое правило «меньший радиус входит в больший» не определяет дальнейший результат
```

Желаемый результат — несколько распределённых точек по всей лесной области, а не случайное подмножество гексов.
Для его получения сначала необходимо зафиксировать правило мержа равных радиусов.

### Большой и маленький радиусы

```text
Candidate A:
    Radius = 8

Candidate B:
    Radius = 3

Distance(A, B) = 6
```

Если паттерны совместимы:

```text
B входит в радиус A
→ B мержится в A
→ Radius A остаётся 8
```

### Кандидаты вне радиусов

```text
Candidate A Radius = 5
Candidate B Radius = 4
Distance(A, B) = 7
```

Ни один центр не находится в необходимом радиусе другого, поэтому обе точки сохраняются.

### Равные радиусы

```text
Candidate A Radius = 5, HexID = 100
Candidate B Radius = 5, HexID = 120
Distance(A, B) = 3
```

Текущая договорённость не определяет, должны ли эти кандидаты объединиться и какой `HexID` должен сохраниться.

### Несовместимые паттерны

```text
Candidate HexID = 100:
    Forest    Priority = 2
    RareRuins Priority = 4
```

Внутри одной маски `RareRuins` выигрывает благодаря большему `Priority`.
Координата остаётся `HexID = 100`, потому что выбирается состав одной и той же точки.

Если `Forest` и `RareRuins` принадлежат двум кандидатам с разными `HexID`, находящимся внутри общего радиуса, это уже пространственный конфликт.
Применение между ними `Priority → FormationWeight`, а также судьба координаты и радиуса остаются `TODO`.

## Инварианты всей цепочки

- Готовый `SpawnPointList` исключает повторный `LocationSearch`.
- Один гекс может соответствовать нескольким паттернам.
- `LocationSearch` сохраняет все совпадения и не выбирает победителя.
- Основное географическое распределение не строится на чистой случайности.
- Все найденные кандидаты участвуют в пространственном формировании.
- Мерж не увеличивает радиус поглощающей точки.
- При нехватке вместимости раньше отбрасываются точки меньшего приоритета.
- Несовместимые паттерны одной логической маски разрешаются сначала через `Priority`, затем через `FormationWeight` при равенстве.
- Правило пространственного конфликта несовместимых кандидатов с разными координатами пока не зафиксировано.
- `FormationWeight`, `SpawnPoint.SpawnChance` и `SpawnUnit.Chance` относятся к разным этапам.
- Физическая вместимость применяется после полного формирования, а не через раннюю остановку линейного прохода.
- `HomeID` равен стабильному индексу окончательной точки.
- После формирования постоянного списка его порядок не перестраивается во время игры.
- `Initial`, `Periodic` и `External` используют готовые точки и не пересчитывают карту кандидатов.

## Короткая формула текущего решения

```text
DistanceMap
    → даёт функциям условий расстояния текущего гекса

LocationSearch
    → вызывает ConditionID каждого SpawnPattern
    → получает true/false
    → устанавливает биты всех совпавших PatternID

CandidatePatternMap
    → хранит 16-битную PatternMask на каждый гекс
    → нулевая маска означает отсутствие кандидата
    → биты соответствуют PatternID 0–15
    → координата определяется HexID карты

SpawnPointFormation
    → рассматривает все кандидаты
    → разрешает маску каждого кандидата через совместимость, Priority и FormationWeight
    → поглощает меньший пространственно совместимый кандидат внутри радиуса большего
    → объединяет совместимые паттерны
    → не увеличивает радиус после мержа
    → при нехватке места удаляет сначала точки меньшего приоритета
    → оставляет правила равных радиусов и конфликта разных координат отдельными TODO

SpawnPointList
    → постоянный результат
    → индекс элемента является HomeID
    → используется Initial, Periodic и External

Runtime
    → равномерно выбирает доступную SpawnPoint
    → проверяет SpawnPoint.SpawnChance
    → рассчитывает SpawnBudget
    → применяет SpawnUnit.Chance при формировании состава
```
