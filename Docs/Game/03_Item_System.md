# Система предметов L&M

Документ описывает структуры предметов, связи между ними, выбор аффиксов, генерацию свойств и расчёт их действия. Для каждой формулы указаны назначение, величины и порядок вычисления.

## 1. Состав данных и связи

| Данные | Назначение | Кто задаёт |
|---|---|---|
| `FItemVisual` | Размеры изображения и адрес спрайта | Заранее подготовленные данные |
| `FBaseItem` | Название, визуал, тип, границы выборки и базовые свойства вида предмета | Заранее подготовленные данные |
| `FItemAffix` | Название аффикса, условия выбора, вес, группа, стоимость и три правила генерации свойств | Заранее подготовленные данные |
| `FItemAffixLevel` | Минимальный и максимальный уровни доступности аффикса | Часть `FItemAffix` |
| `FItemAffixProperty` | Тип свойства, дополнительный параметр и диапазон его величины | Часть `FItemAffix` |
| `FItem` | Базовый вид, качество, выбранные аффиксы, состояние и полученные свойства экземпляра | Создаётся в рантайме |
| `FItemProperty` | Тип свойства и его фактическая величина | В базовом описании задаётся заранее, в экземпляре получается при генерации |
| `FItemID` | Идентификатор предмета, используемый в том числе экипировкой | Ссылка на предмет, а не описание его свойств |

```text
FCharacterEquipment → FItemID
                         │
                         ▼
                       FItem
                         ├─ BaseItem → FBaseItem
                         │                ├─ Name → текст названия
                         │                ├─ Visual → FItemVisual → спрайт
                         │                └─ Properties → базовые FItemProperty
                         ├─ Prefix → список префиксов FItemAffix
                         ├─ Suffix → список суффиксов FItemAffix
                         └─ Properties → полученные FItemProperty
```

Префиксы и суффиксы находятся в отдельных списках одной структуры. При выборе аффикса сохраняется его индекс. Его правила создают значения свойств экземпляра. Исходный `FBaseItem` и его свойства при этом не изменяются.

Индекс не является адресом. Способ получения записи по индексу должен учитывать размер её структуры. Для записей переменной длины нельзя умножать индекс только на размер шапки.

## 2. Типы, качества и классы

### 2.1. Тип предмета

`FBaseItem.Type` хранит одно значение из таблицы. В масках аффикса то же значение используется как номер бита.

| Константа | Значение | Тип | Допустимое размещение |
|---|---:|---|---|
| `ITEM_TYPE_HEAD` | `0x00` | «голова» | `Head` |
| `ITEM_TYPE_BREAST` | `0x01` | «грудь» | `Breast` |
| `ITEM_TYPE_AMULET` | `0x02` | «амулет» | `Amulet` |
| `ITEM_TYPE_RING` | `0x03` | «кольцо» | `LeftRing` или `RightRing` |
| `ITEM_TYPE_LEFT_HAND` | `0x04` | «левая рука» | `LeftHand` |
| `ITEM_TYPE_RIGHT_HAND` | `0x05` | «правая рука» | `RightHand` или `LeftHand` |
| `ITEM_TYPE_TWO_HANDED` | `0x06` | «двуручный» | Одновременно занимает `RightHand` и `LeftHand` |
| `ITEM_TYPE_BELT` | `0x07` | «пояс» | `Belt` |
| `ITEM_TYPE_SHOULDER_PAD` | `0x08` | «наплечник/плащ» | `ShoulderPad` |
| `ITEM_TYPE_BOOT` | `0x09` | «обувь» | `Boot` |

Имена слотов соответствуют FCharacterEquipment. Тип предмета и текущее место экземпляра — разные данные: кольцо сохраняет тип «кольцо» при переносе из левого кольцевого слота в правый.

### 2.2. Качество

| Константа | Значение | Качество |
|---|---:|---|
| `ITEM_QUALITY_NORMAL` | `0x00` | Обычный |
| `ITEM_QUALITY_MAGIC` | `0x01` | Магический |
| `ITEM_QUALITY_RARE` | `0x02` | Редкий |
| `ITEM_QUALITY_UNIQUE` | `0x03` | Уникальный |
| `ITEM_QUALITY_SET` | `0x04` | Сетовый |

`FItem.Quality` содержит одно значение качества. `FItemAffix.Quality` содержит маску разрешённых качеств. Записывать индекс качества непосредственно в маску нельзя: для магического качества индекс равен `1`, а битовая маска равна `1 << 1 = 2`.

Цвет названия предмета определяется качеством экземпляра `FItem.Quality`.

### 2.3. Класс

Значения приведены по текущему файлу.

| Константа | Значение | Класс |
|---|---:|---|
| `Character.Class.Druid` | `0x00` | Друид |
| `Character.Class.Wizard` | `0x01` | Волшебник |
| `Character.Class.Warlock` | `0x02` | Колдун |
| `Character.Class.Witch` | `0x03` | Ведьмак |
| `Character.Class.DeathKnight` | `0x04` | Рыцарь смерти |
| `Character.Class.Overlord` | `0x05` | Повелитель |
| `Character.Class.Necromancer` | `0x06` | Некромант |
| `Character.Class.Any` | `0x07` | Любой класс |

Класс персонажа и гендер упакованы в один байт персонажа. При сравнении класса гендер не участвует. Для проверки аффикса применяется значение `Character.Class.Any` из исходника, а не отдельно записанный числовой литерал.

## 3. Структуры и поля

Смещения ниже считаются от начала соответствующей структуры. `DB` занимает один байт, `DW` и `FValue` — два. У `FValue` младший байт находится первым. Объявления задают формат данных; начальные нули не определяют отдельные правила генерации или значения «пусто».

Для фактических величин свойств, границ `FBaseItem.Min/Max`, границ `FItemAffixProperty.Min/Max` и `CostAdd` используются значения со знаком от `−32768` до `32767`. Сам `FValue` описывает только два байта, их смысл задаёт поле-владелец. Чтение значения со знаком:

```text
U = Low + 256 × High
V = U, если U < 32768
V = U − 65536, иначе
```

`Low` и `High` — младший и старший байты, каждый от `0` до `255`. `U` — их беззнаковое объединение, `V` — величина со знаком. Например, байты `FF FF` дают `U = 65535`, `V = −1`. Адреса и `Param` не становятся отрицательными из-за такого способа чтения свойств.

### 3.1. FItemVisual — шапка спрайта

Размер — **4 байта**. Шапка размещается рядом с графикой. Формат спрайта — OR/XOR с атрибутами.

| Поле | Смещение | Размер | Что хранит | Где используется |
|---|---:|---:|---|---|
| `Size.Width` | 0 | 1 | Ширина спрайта в знакоместах | Ширина выводимого изображения |
| `Size.Height` | 1 | 1 | Высота спрайта в знакоместах | Высота выводимого изображения |
| `Adr` | 2 | 2 | Адрес спрайта | Чтение графики при отрисовке |

`Size.Width` и `Size.Height` задают ширину и высоту спрайта в знакоместах. Одно знакоместо — 8×8 пикселей. Например, размеры 2×3 означают изображение 16×24 пикселя.

### 3.2. FItemProperty — фактическое свойство

Размер — **4 байта**.

| Поле | Смещение | Размер | Что хранит | Где используется |
|---|---:|---:|---|---|
| `Type` | 0 | 1 | Тип свойства `ITEM_PROPERTY_` | Определяет, какую характеристику или эффект задаёт `Value` |
| `Value` | 1 | 2 | Фактическая величина со знаком | Числовой бонус, штраф или другая величина по правилам `Type` |
| `Dummy` | 3 | 1 | Резервный байт | Не используется |

В базовом описании `Value` заранее задан. В экземпляре это уже полученный результат, а не минимум или максимум генерации. `Dummy` не является индексом аффикса.

### FBaseItem — базовое описание предмета

Постоянная часть — **9 байт**. Непосредственно за ней следуют свойства.

| Поле | Смещение | Размер | Что хранит | Где используется |
|---|---:|---:|---|---|
| `Name` | 0 | 2 | Адрес текста названия | Формирование названия предмета |
| `Visual` | 2 | 1 | Индекс `FItemVisual` в линейном массиве | Получение шапки спрайта |
| `Type` | 3 | 1 | Одно значение `ITEM_TYPE_` | Допустимое размещение в экипировке и выбор подходящих аффиксов |
| `Min` | 4 | 2 | Минимальное значение для выборки | Нижняя граница диапазона, назначение зависит от `Type` |
| `Max` | 6 | 2 | Максимальное значение для выборки | Верхняя граница диапазона, назначение зависит от `Type` |
| `PropertiesNum` | 8 | 1 | Количество базовых свойств | Обход массива и вычисление полной длины записи |
| `Properties` | 9 | По количеству | Начало встроенного массива `FItemProperty` | Получение базовых свойств этого вида |

`Properties` — метка начала массива без выделения памяти. Элементы размещаются после шапки при описании конкретной записи. У каждого базового вида своё количество элементов.

`Min` и `Max` задают один диапазон для базового предмета. Что именно выбирается в этом диапазоне, определяет `Type`. Свойства в массиве `Properties` хранятся отдельно и имеют собственные фактические значения.

Базовое описание общее для экземпляров. Генерация и перемещение экземпляра не переписывают эту запись.

### 3.4. FItemAffixLevel — диапазон уровня доступности аффикса

Размер — **2 байта**.

| Поле | Смещение | Размер | Что хранит | Где используется |
|---|---:|---:|---|---|
| `Min` | 0 | 1 | Минимальный уровень доступности аффикса | Аффикс доступен при уровне не ниже этого значения |
| `Max` | 1 | 1 | Максимальный уровень доступности аффикса | Аффикс доступен при уровне не выше этого значения |

Аффикс доступен для выбора в указанном диапазоне уровней включительно. Например, при `Min = 5` и `Max = 10` он доступен на уровнях 5–10. Уровень для сравнения передаётся при выборе аффикса. Это не требуемый уровень героя для экипировки и не величина бонуса. Отдельного поля уровня в `FItem` сейчас нет.

### 3.5. FItemAffixProperty — правило генерации свойства

Размер — **7 байт**.

| Поле | Смещение | Размер | Что хранит | Где используется |
|---|---:|---:|---|---|
| `Type` | 0 | 1 | Тип создаваемого свойства `ITEM_PROPERTY_` | Копируется в свойство экземпляра и определяет обработку |
| `Param` | 1 | 2 | Дополнительный параметр свойства | Например, номер умения, которому добавляется бонус |
| `Min` | 3 | 2 | Минимальная величина | Нижняя граница случайного выбора |
| `Max` | 5 | 2 | Максимальная величина | Верхняя граница случайного выбора |

Пример для бонуса умению: `Type = SINGLESKILL`, `Param` выбирает конкретное умение, `Min = 1`, `Max = 3` задают величину бонуса. `Param` не равен величине бонуса. Для свойства без дополнительного параметра используется `0`.

После генерации в `FItemProperty` записываются `Type` и полученная величина `Value`. Поля `Param` в этой структуре нет. Если параметр требуется при применении, его можно получить из правила исходного аффикса по сохранённому индексу и порядку блоков; перестановка или слияние записей нарушит такую связь.

### 3.6. FItemAffix — описание аффикса

Размер — **37 байт**. Одна структура используется в двух отдельных списках: префиксов и суффиксов.

| Поле | Смещение | Размер | Что хранит | Где используется |
|---|---:|---:|---|---|
| `Level` | 0 | 2 | Диапазон уровня доступности аффикса `FItemAffixLevel` | Выбор аффикса в пределах `Level.Min` и `Level.Max` |
| `IncludeTypes` | 2 | 2 | Маска разрешённых типов предметов | Допускаемые типы предметов |
| `ExcludeTypes` | 4 | 2 | Маска запрещённых типов предметов | Исключённые типы предметов |
| `Quality` | 6 | 1 | Маска разрешённых качеств предметов | Допускаемые качества предметов |
| `Class` | 7 | 1 | Разрешённый класс | Ограничение выбора аффикса по классу |
| `Name` | 8 | 2 | Адрес текста названия аффикса | Формирование названия предмета |
| `Frequency` | 10 | 1 | Относительный вес | Вероятность выбора среди подходящих аффиксов |
| `Group` | 11 | 1 | Номер группы несовместимости | Исключение сочетаний аффиксов одной группы |
| `CostMultiply` | 12 | 2 | Параметр множителя стоимости | Расчёт торговой цены |
| `CostAdd` | 14 | 2 | Параметр прибавки к стоимости | Расчёт торговой цены |
| `Property1` | 16 | 7 | Первое правило генерации | Создание первой записи свойства |
| `Property2` | 23 | 7 | Второе правило генерации | Создание следующей записи свойства |
| `Property3` | 30 | 7 | Третье правило генерации | Создание следующей записи свойства |

Три правила встроены непосредственно в аффикс. Число правил аффикса и число выбранных аффиксов — разные величины.

В структуре три блока свойств. Неиспользуемый блок имеет `Type = ITEM_PROPERTY_NONE`, значение константы — `0xFF`. Такой блок пропускается, его `Param`, `Min` и `Max` не обрабатываются. Если аффикс даёт одно свойство, остальные два блока помечаются `ITEM_PROPERTY_NONE`.

Поля `CostMultiply` и `CostAdd` предназначены для изменения торговой цены.

### 3.7. FItem — экземпляр

Постоянная часть — **6 байт**. Затем следуют полученные свойства.

| Поле | Смещение | Размер | Что хранит | Где используется |
|---|---:|---:|---|---|
| `BaseItem` | 0 | 1 | Индекс `FBaseItem` | Получение базового описания и его неизменных свойств |
| `Quality` | 1 | 1 | Одно значение `ITEM_QUALITY_` | Выбор подходящих аффиксов и оформление названия по качеству |
| `Prefix` | 2 | 1 | Массив из одного индекса префикса | Получение имени и правил выбранного аффикса |
| `Suffix` | 3 | 1 | Массив из одного индекса суффикса | Получение имени и правил выбранного аффикса |
| `State` | 4 | 1 | Состояние предмета | Управление размещением, экипировкой и переносом |
| `PropertiesNum` | 5 | 1 | Количество полученных свойств | Обход массива и вычисление полной длины записи |
| `Properties` | 6 | По количеству | Начало встроенного массива `FItemProperty` | Хранение фактических результатов генерации |

`Prefix` и `Suffix` — массивы индексов, сейчас по одному элементу в каждом. По индексу получается запись из соответствующего списка аффиксов.

Свойства сохраняются последовательно по выбранным аффиксам и их блокам. При записи и восстановлении связи с `Param` используется один и тот же порядок аффиксов и их блоков.

### 3.8. FItemID и экипировка

`ID` занимает один байт и обозначает предмет. `FCharacterEquipment` содержит десять таких ссылок: `Head`, `Breast`, `Amulet`, `ShoulderPad`, `Belt`, `LeftHand`, `RightHand`, `LeftRing`, `RightRing`, `Boot`.

`FItemID.ID` и `FItem.BaseItem` имеют разный смысл: первый обозначает предмет, второй — его базовое описание. Два разных экземпляра могут ссылаться на один базовый вид. Способ поиска экземпляра по `ID` здесь не устанавливается.

## 4. Адресация и обход

### 4.1. Записи фиксированной длины

```text
A = T + i × S
```

| Член | Значение |
|---|---|
| `A` | Адрес выбранной записи |
| `T` | Начало соответствующего линейного массива |
| `i` | Индекс записи, начиная с нуля |
| `S` | Размер одной записи |

Для визуала `S = 4`, для аффикса `S = 37`. Например, визуал с индексом `3` находится на `12` байт дальше начала массива визуалов. Размер записи позволяет вычислить смещение выбранного элемента от начала массива.

### 4.2. Свойства внутри записи

```text
A_property = A_record + H + k × 4
RecordSize = H + N × 4
A_next     = A_record + RecordSize
```

| Член | Значение |
|---|---|
| `A_record` | Начало конкретной записи предмета |
| `H` | Размер шапки: `9` у `FBaseItem`, `6` у `FItem` |
| `k` | Номер свойства, `0 ≤ k < N` |
| `N` | Значение `PropertiesNum` этой записи |
| `4` | Размер `FItemProperty` |
| `A_next` | Начало следующей записи при последовательном размещении |

Пример: экземпляр с тремя свойствами занимает `6 + 3 × 4 = 18` байт. Свойства начинаются на смещениях `6`, `10`, `14`.

Для поиска `FBaseItem` по индексу возможен последовательный проход с вычислением `A_next` либо отдельная таблица адресов. Формула `T + индекс × 9` неверна, поскольку игнорирует встроенные свойства.

Восемь свойств занимают `8 × 4 = 32` байта. В текущей структуре длина массива задаётся `PropertiesNum`, фиксированного массива на восемь элементов нет.

## 5. Выбор аффикса

### 5.1. Проверка условий

В формулах `A` — аффикс, `B` — базовое описание предмета, `I` — создаваемый экземпляр, `L` — уровень подбора аффиксов, `C` — класс без гендерного бита.

```text
TypeBit    = 1 << B.Type
QualityBit = 1 << I.Quality

TypeAllowed    = (A.IncludeTypes & TypeBit) != 0
TypeExcluded   = (A.ExcludeTypes & TypeBit) != 0
QualityAllowed = (A.Quality & QualityBit) != 0
LevelAllowed   = A.Level.Min ≤ L ≤ A.Level.Max
ClassAllowed   = (A.Class == Character.Class.Any) или (A.Class == C)

Allowed = TypeAllowed и не TypeExcluded и QualityAllowed
          и LevelAllowed и ClassAllowed и GroupAllowed
```

`<<` — сдвиг единицы на номер бита. `&` — побитовое И. `GroupAllowed` означает отсутствие уже выбранного аффикса с той же группой. Частота `0` исключает запись из случайного выбора, поскольку ей не достаётся ни одного исхода.

Пример: для типа «правая рука» индекс равен `5`, значит `TypeBit = 1 << 5 = 0x0020`. Аффикс должен иметь этот бит в `IncludeTypes` и не иметь его в `ExcludeTypes`. Тип предмета не превращается в «левая рука» при переносе в левый слот.

Класс `C` передаётся при выборе аффикса.

### 5.2. Группа несовместимости

Если уже выбран аффикс группы `G`, очередной аффикс с тем же `G` не допускается. Например, две ступени повышения одной характеристики можно отнести к одной группе, чтобы они не выпадали вместе.

Группа — не вероятность и не тип свойства. Она запрещает сочетание целых аффиксов.

### 5.3. Выбор по весам

Согласованная схема взвешенного выбора:

```text
W = w₀ + w₁ + ... + wₙ₋₁
r = случайное целое от 0 до W − 1
S₀ = 0
Sⱼ = w₀ + ... + wⱼ₋₁

выбран j, для которого Sⱼ ≤ r < Sⱼ + wⱼ
Pⱼ = wⱼ / W
```

| Член | Значение |
|---|---|
| `n` | Количество подходящих записей |
| `wⱼ` | `Frequency` записи с номером `j` |
| `W` | Сумма весов подходящих записей, должна быть больше нуля |
| `r` | Один случайный номер в суммарном диапазоне |
| `Sⱼ` | Начало диапазона исходов этой записи |
| `Pⱼ` | Вероятность выбрать запись |

| Аффикс | Вес | Диапазон `r` | Вероятность |
|---|---:|---|---:|
| A | 200 | 0–199 | 40% |
| B | 100 | 200–299 | 20% |
| C | 200 | 300–499 | 40% |

Здесь `W = 500`. Каждый вес помещается в байт, сумма и случайное число требуют двух байт. Согласован расчёт суммы в 16 битах, поэтому `W` не должен превышать `65535`. При `W = 0` выбрать аффикс нельзя. Сортировка по весам не требуется.

## 6. Генерация величин и запись результата

Для действующего блока `FItemAffixProperty`:

```text
N = Max − Min + 1
u = случайное целое от 0 до N − 1
V = Min + u
```

`Min` и `Max` — включённые границы диапазона. `N` — число возможных целых результатов. `u` — случайное смещение, `V` — полученная величина.

Например, `Min = 2`, `Max = 5`: `N = 4`, возможны `2`, `3`, `4`, `5`. При `u = 2` получаем `V = 4`. Если `Min = Max`, результат всегда равен этому значению.

Ширину `N` нельзя ограничивать размером сохраняемой величины: полный диапазон от `−32768` до `32767` содержит `65536` исходов. Промежуточные вычисления должны вмещать количество возможных результатов.

Порядок обработки предмета:

1. Получить базовое описание по `BaseItem`. Его данные не изменять.
2. Получить качество экземпляра, уровень подбора аффиксов и класс для сравнения.
3. Отфильтровать и выбрать нужные аффиксы, сохранить индексы в `Prefix` и `Suffix`.
4. Обойти действующие блоки выбранных аффиксов в одинаковом установленном порядке.
5. Для каждого блока получить `V`, записать `Type` и `Value = V` в очередной `FItemProperty` экземпляра.
6. Записать фактическое количество результатов в `PropertiesNum`.

Повторное открытие подсказки и перемещение предмета не запускают генерацию заново. Два экземпляра с одним аффиксом могут хранить разные результаты.

Пример: префикс содержит два действующих блока, суффикс — один. Получаются три записи свойств. Для примера ниже префикс обработан первым:

| Позиция | Откуда правило | Что хранится у экземпляра |
|---:|---|---|
| 0 | Префикс, первый блок | Тип первого свойства и выпавшая величина |
| 1 | Префикс, второй блок | Тип второго свойства и выпавшая величина |
| 2 | Суффикс, первый блок | Тип третьего свойства и выпавшая величина |

Значения не приходится заново искать внутри диапазонов аффикса. Для простого числового свойства достаточно `Type` и `Value`. Обращение к правилу нужно, когда требуется его `Param`, название или другие общие данные.

## 7. Свойства и применение величин

Макрос `REG_ITEM_PROPERTY_ID` назначает номера последовательно. При перестановке списка меняются номера.

Величина каждого свойства хранится отдельно от его типа. Равные числа у разных типов не означают одинаковое действие: `+10` атаки и `10%` сопротивления имеют разные единицы и разные формулы.

### 7.1. Собственные параметры существ и бонусы предметов отряда

У каждого существа есть собственные параметры: здоровье, рейтинг атаки, защита, урон и сопротивления. Предметы добавляют к ним общий бонус отряда. Собственные параметры разных существ сохраняются разными, даже когда бонус предметов у них одинаковый.

Для свойства, являющегося числовой прибавкой:

```text
ItemBonus(j, t) = BaseBonus(j, t) + InstanceBonus(j, t)
TroopBonus(t)   = сумма ItemBonus(j, t) по действующим предметам отряда
X_result(c, t)  = X_own(c, t) + TroopBonus(t)
```

| Член | Значение |
|---|---|
| `j` | Предмет, бонусы которого действуют на отряд |
| `t` | Тип свойства `ITEM_PROPERTY_` |
| `c` | Существо, для которого рассчитывается характеристика |
| `BaseBonus(j, t)` | Сумма величин типа `t` из свойств `FBaseItem` этого предмета |
| `InstanceBonus(j, t)` | Сумма полученных величин типа `t` из свойств его `FItem` |
| `ItemBonus(j, t)` | Общий вклад одного предмета по этому свойству |
| `TroopBonus(t)` | Суммарный бонус действующих предметов, распространяемый на весь отряд |
| `X_own(c, t)` | Собственное значение характеристики существа без бонусов предметов |
| `X_result(c, t)` | Значение характеристики существа после прибавки бонуса предметов отряда |

Пример: два предмета дают отряду `+2` и `+3` максимального здоровья. Общий бонус равен `5`. Существо с собственным здоровьем `20` получает максимум `25`, существо со здоровьем `40` — максимум `45`. Бонус не делится между существами.

Общий бонус рассчитывается из базовых свойств предметов и дополнительных свойств их экземпляров. Идентификаторы `Prefix` и `Suffix` не дают ещё одну копию тех же бонусов: их полученные величины уже записаны в `FItem.Properties`. Базовые свойства предмета и собственные параметры существа при расчёте не переписываются.

При изменении набора действующих предметов итог вычисляется заново от собственных параметров. Повторное применение расчёта к уже усиленному результату ошибочно: оно повторно прибавит тот же бонус.

Эта схема относится к свойствам, распространяющимся на существ. Прибавки атаки, защиты, силы заклинаний и знаний героя сначала изменяют характеристики героя; их дальнейшее влияние на существ определяется отдельными правилами. Процентные свойства отряда суммируются как проценты и применяются к соответствующему параметру, а не прибавляются к нему как обычное число.

## 8. Формулы боевых свойств

В этом разделе описаны расчёты попадания, процентных бонусов, сопротивлений и вероятностных эффектов. Условия применения указаны перед каждой формулой.

### 8.1. Шанс попадания и защита

Перед расчётом шанса попадания определяются характеристики конкретных участников:

```text
AR  = AR_own + TroopBonus(TOHIT) атакующего отряда
DEF = floor(DEF_own × (100 + TroopBonus(ARMOR_PERCENT) защищающегося отряда) / 100)
```

`AR_own` — собственный рейтинг атаки атакующего существа. `DEF_own` — собственная защита существа-цели. `TroopBonus(TOHIT)` — общая числовая прибавка рейтинга атаки от предметов атакующей стороны. `TroopBonus(ARMOR_PERCENT)` — общий процент увеличения защиты от предметов защищающейся стороны. Бонусы сторон рассчитываются независимо.

Применение: атака, которая проверяет рейтинг атаки против защиты цели. При неотрицательных рейтингах и положительных уровнях математическая зависимость:

```text
P_math = 100 × AR / (AR + DEF) × 2 × LA / (LA + LD)
```

| Член | Что означает | На что влияет |
|---|---|---|
| `AR` | Итоговый рейтинг атаки атакующего | Увеличение повышает долю успешных попаданий |
| `DEF` | Итоговый показатель защиты цели | Увеличение понижает долю успешных попаданий |
| `LA` | Уровень атакующего | Относительное преимущество атакующего по уровню |
| `LD` | Уровень цели | Относительное преимущество защищающегося по уровню |
| `100` | Перевод доли в проценты | `50` означает шанс 50% |
| `2` | Нормировка множителя уровней | При одинаковых уровнях множитель уровней равен 1 |

Порядок целочисленного вычисления:

```text
если AR + DEF > 0:
    Q = floor(100 × AR / (AR + DEF))
иначе:
    Q = 100

P = clamp(floor(2 × LA × Q / (LA + LD)), 5, 95)
r = случайное целое от 0 до 99
попадание происходит, если r < P
```

`Q` — целочисленная промежуточная доля. `floor` округляет вниз для приведённых неотрицательных чисел. `clamp(x, a, b)` ограничивает результат снизу `a` и сверху `b`. Пределы `5` и `95` относятся к этой обычной проверке, а не к любому способу нанесения урона.

Пример: `AR = 1000`, `DEF = 500`, `LA = LD = 20`. Математически получается около `66,67%`. Код сначала получает `Q = 66`, затем `P = 66`. При `r = 65` атака попадает, при `r = 66` — нет.

Защита уменьшает шанс попасть, но не размер уже попавшего удара. Формула определяется способом атаки, а не только типом урона: стихийная добавка к обычному удару не отменяет проверку попадания этого удара. Заклинание без проверки AR/DEF не обязано физически пересечь цель своим снарядом.

### 8.2. Процентное усиление показателя

Процентный бонус предметов отряда применяется к собственной величине существа с учётом числовых прибавок:

```text
X_before = X_own + FlatBonus
X_after  = floor(X_before × (100 + E) / 100)
```

`X_own` — собственная величина существа. `FlatBonus` — общая числовая прибавка действующих предметов к этой величине, если такой тип прибавки предусмотрен. `X_before` — результат до процентного усиления. `E` — суммарный процент увеличения от предметов отряда. `X_after` — результат этапа. Например, собственная величина `180`, числовой бонус `20` и процентный бонус `50` дают `X_before = 200`, `X_after = 300`.

### 8.3. Усиление физического урона

Сначала собственный диапазон урона существа дополняется числовыми бонусами предметов отряда, затем применяются процентные бонусы:

```text
Dmin_before = Dmin_own + TroopBonus(MINDAMAGE)
Dmax_before = Dmax_own + TroopBonus(MAXDAMAGE)
E           = TroopBonus(DAMAGE_PERCENT)
Emax        = TroopBonus(MAXDAMAGE_PERCENT)

Dmin_after = floor(Dmin_before × (100 + E) / 100)
Dmax_after = floor(Dmax_before × (100 + E + Emax) / 100)
```

| Член | Значение |
|---|---|
| `Dmin_own`, `Dmax_own` | Собственные минимальный и максимальный урон существа без бонусов предметов |
| `TroopBonus(MINDAMAGE)` | Общая числовая прибавка к минимальному урону от предметов отряда |
| `TroopBonus(MAXDAMAGE)` | Общая числовая прибавка к максимальному урону от предметов отряда |
| `Dmin_before`, `Dmax_before` | Границы физического урона до рассматриваемого усиления |
| `E` | Суммарный процент увеличения обеих границ от предметов отряда |
| `Emax` | Суммарный дополнительный процент только верхней границы от предметов отряда |
| `Dmin_after`, `Dmax_after` | Границы после этого этапа |

Пример: собственный урон существа `8–15`, предметы отряда дают `+2` к минимальному и `+5` к максимальному урону, а также `+50%` общего урона. Получаем `Dmin_before = 10`, `Dmax_before = 20`, затем итоговый диапазон `15–30`.

При исходном диапазоне `10–20`, `E = 50`, `Emax = 0` получаем `15–30`. При `E = 0`, `Emax = 50` получаем `10–30`. Сложение `E + Emax` здесь относится к одному процентному этапу, а не к последовательному умножению двух независимых усилителей.

`DAMAGE_PERCENT` увеличивает обе границы урона, `MAXDAMAGE_PERCENT` — только верхнюю. В нашей системе эти бонусы действуют на существ.

### 8.4. Сопротивление и входящий урон

Для одного компонента урона после предыдущих этапов защиты, без поглощения и специальных исключений:

```text
R_total = R_own + TroopBonus(сопротивление выбранному типу урона)
R       = R_total после применения пределов сопротивления
D_after = max(0, floor(D_before × (100 − R) / 100))
```

| Член | Значение |
|---|---|
| `D_before` | Урон выбранного типа перед применением сопротивления |
| `R_own` | Собственное сопротивление существа-цели выбранному типу урона |
| `TroopBonus(сопротивление выбранному типу урона)` | Суммарная прибавка сопротивления от предметов защищающегося отряда |
| `R_total` | Собственное сопротивление с прибавкой предметов до применения пределов |
| `R` | Уже рассчитанное эффективное сопротивление этому типу, в процентах |
| `D_after` | Оставшийся урон этого типа |
| `max(0, x)` | Не позволяет получить отрицательный урон из этой формулы |

Для `D_before = 100`: при `R = 20` остаётся `80`, при `R = −20` получается `120`, при `R = 100` — `0`. Сопротивление огню применяется к огненной части, физическое — к физической. После раздельной обработки компоненты суммируются.

Например, собственное сопротивление огню `10%` и бонус предметов отряда `20%` дают `R_total = 30%`. Если предел не ограничивает это значение, из `100` огненного урона остаётся `70`.

`ARMOR_PERCENT` увеличивает показатель для проверки попадания. `DAMAGERESIST` уменьшает физический компонент уже получаемого урона. Это разные действия.

В формулу подставляется сопротивление после применения его ограничений.

### 8.5. Смертельный удар и события

Пример проверки смертельного удара, удваивающего физический урон:

```text
P_total = P_own + TroopBonus(DEADLYSTRIKE)
P = clamp(P_total, 0, 100)
r = случайное целое от 0 до 99
если r < P: физический урон удваивается
```

`P_own` — собственный шанс этого эффекта у существа, если он есть, иначе `0`. `TroopBonus(DEADLYSTRIKE)` — сумма прибавок шанса от предметов отряда. `P_total` — их сумма до ограничения, `P` — итоговый шанс в процентах. `r` определяет один исход проверки. Удвоение относится к физической части. Это не мгновенное убийство и не дополнительный бросок самого базового диапазона урона.

События применения умений различаются: `SKILLONATTACK` относится к началу/факту атаки, `SKILLONHIT` — к успешному попаданию, `SKILLONGETHIT` — к полученному удару. Вероятность, номер умения и его сила требуют своего правила параметров. Число в `Value` нельзя автоматически назначить одновременно всем этим значениям.

## 9. Название предмета

Базовое название читается по адресу `FBaseItem.Name`. Названия выбранного префикса и суффикса читаются по адресам `Name` их описаний.

Полученные свойства читаются из `FItem.Properties`. Описание аффикса не заменяет сохранённый результат броска. Название и числовой список бонусов решают разные задачи интерфейса.
